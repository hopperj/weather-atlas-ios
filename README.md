# Weather Atlas for iPhone

Native SwiftUI / MapKit client for the Weather Atlas server. Requires iOS 17+ and
Xcode 16 or newer (verified with Xcode 26.3). The checked-in Xcode project has no
third-party iOS dependencies.

Open WeatherAtlas.xcodeproj, select the WeatherAtlas scheme and an iPhone
simulator, then Run. On a physical iPhone, select your development team under
Signing & Capabilities.

## App icon

The selected Crimson Sky maple-leaf/cloud icon is included in
`WeatherAtlas/Resources/Assets.xcassets/AppIcon.appiconset`. Its opaque
1024 × 1024 PNG is copied from the web app's selected export, without changing
the artwork (SHA-256:
`ba03e32a335aeddf6936511d5fbbb367cabb0e475bc9ca2664105759f1c10c2f`).
Xcode generates the smaller iPhone icon sizes from this single asset.

In Xcode, open Resources → Assets → AppIcon to view or replace it. The app
target's App Icons Source is `AppIcon` in both Debug and Release, and the
asset catalog is included in the app's Resources build phase. The matching
setting is also recorded in `project.yml` so generated projects include it.
Build and Run on the phone to install the new icon; refreshing the website
does not update the native application. No physical-device signing or
installation was performed for this change.

Icon verification (2026-09-07, Xcode 26.3): the Debug simulator build and
unsigned Release iOS-device build succeeded. All 43 unit tests passed on the
iPhone 17 Pro simulator, including a check of the packaged iPhone/iPad primary
icon metadata and compiled asset catalog. The compiled PNG was visually checked
against the selected artwork. UI tests were not rerun for this asset-only change.
That icon-only build reported an unrelated interface-orientation warning, which
is resolved by the orientation configuration described below.

## Target devices and screen orientations

Build 1.0 (16) targets **iPhone only** (`TARGETED_DEVICE_FAMILY = 1`) for the app,
widget and test targets, in both Debug and Release. Mac Catalyst and the
Mac/Apple Vision "Designed for iPhone & iPad" Xcode destinations are disabled.
These settings are recorded in `project.yml` and the regenerated Xcode project.

The app retains portrait and both landscape orientations on iPhone. Its obsolete
iPad-specific orientation declarations have been removed. `UIDeviceFamily` is
generated by Xcode, not manually inserted in the source plist. Tests inspect
the packaged app and widget family, phone orientation declarations and phone icon.
No full-screen requirement, artificial hardware requirement or new permission
was added. Signing identities and the existing App Group are unchanged.

iPhone-only targeting removes native iPad support, but is not an iPad execution
ban: [iPadOS may still run an iPhone app in compatibility mode](https://developer.apple.com/forums/thread/727753).
Xcode may therefore retain generated iPad compatibility icon entries; the
authoritative packaged device-family value is `[1]`. Mac and Apple
Vision App Store availability is managed separately in App Store Connect; this
change only configures the project and builds, not an App Store listing.

Verified September 8, 2026: all 155 simulator unit tests pass; the signed Release
iPhone build succeeds without warnings. The packaged Debug and Release app/widget
declare only device family `[1]`. Build 16 is installed on the connected iPhone;
no physical-device UI automation or permission resets were performed.

## Secure service connection

Build **1.0 (14)** uses the fixed public endpoint
**https://weatheratlas.ioresearch.ca** in both the app and widget extension.
Settings no longer contains a server-address field or Connect button. Existing
server preferences cannot override the endpoint, and there is no HTTP fallback.
No local-network permission or insecure transport exception is needed.

The first upgraded launch migrates saved places, forecast selection/default,
location-following state, map pin and the two forecast snapshots from recognized
legacy Weather Atlas addresses. Existing HTTPS preferences take precedence;
original data is retained. Unrelated custom-server data is not relabeled as
Weather Atlas data. Widget settings are normalized before networking, even if
the widget runs before the updated app is opened.

Install the rebuilt app through Xcode or distribute the new archive to apply the
change; Settings → About should show **1.0 (14)**. No manual connection setup is
required. See [fixed HTTPS endpoint](docs/fixed-https-endpoint.md).

## Server boundary

The iPhone only reads JSON and display tiles. It does not contact weather providers,
collect observations, parse GRIB/XML, calculate meteorology, interpolate missing
hours, or run ETL. Weather requests and tile requests share a same-origin policy;
external URLs and cross-origin redirects are rejected. Apple Maps separately
supplies the basemap.

URLSession caches map display responses subject to server cache headers. Forecasts
use the explicit launch snapshot described above and check the server on refresh.
This is not an offline weather archive; forecasts require connectivity to refresh. Favorites
remain available locally. Dates are displayed in the device time zone; ECCC
period names are retained as supplied. Hourly model predictions are identified
separately from the official regional bulletin.

Automatic local forecasts require the server's GET /api/v1/forecast/nearest
endpoint. It uses the nearest collected region reference point within 200 km,
not a hyperlocal forecast. If the deployed server predates this endpoint, rebuild
and deploy the weather API; the app temporarily shows Halifax from the existing
regional catalogue meanwhile. This fallback is not a claim that the phone is in
Halifax. iOS prompts for location only when permission has not yet been decided;
an existing permission is reused, while denied access offers iPhone Settings.
The server extensions, migration and activation instructions are documented in
[the imagery and iOS server guide](../weatherapp/docs/imagery-and-ios.md).

## Development and verification

project.yml is the XcodeGen source of truth. Regenerate the checked-in project
after adding files or changing settings. Before regenerating, copy any signing
team or bundle-identifier changes made directly in Xcode into `project.yml` if
you want to retain them. The icon integration updates the existing project in
place to preserve those local settings:

    cd weatheratlas-ios
    xcodegen generate
    xcodebuild -project WeatherAtlas.xcodeproj -scheme WeatherAtlas \
      -sdk iphonesimulator CODE_SIGNING_ALLOWED=NO build

For automated tests, start the synthetic, loopback-only fixture server in a
separate terminal. It is a test utility and is not bundled in the app:

    python3 weatheratlas-ios/Support/fixture_server.py

Then select a simulator returned by xcrun simctl list devices available:

    cd weatheratlas-ios
    xcodebuild -project WeatherAtlas.xcodeproj -scheme WeatherAtlas \
      -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
      CODE_SIGNING_ALLOWED=NO test

The tests cover origin restrictions, timestamp/null-value decoding, analysis
semantics, server-specific favorites, forecast/map/settings navigation, wind and
hotspot controls, HTTP connection settings, and map-to-nearby-forecast navigation.
Unit tests also cover the corrected default, one-time port migration and saved-place
preservation, bundled primary icon metadata and device-family targeting for iPhone, location
permission/lifecycle, manual forecast persistence, missing
coverage, and late responses after a manual selection. Precipitation tests cover
issued ranges and snow units, omitted POP with complete model totals,
conservative wet-weather wording, missing/zero/trace amounts, bulletin matching,
independent request failures and late responses after changing locations. UI
coverage verifies the Daily / Nightly and Hourly toggle below the map button,
all 72 hourly rows, and switching back to the daily precipitation cards. Hourly plot
tests verify each server-field mapping, units, missing/zero/non-finite values,
removal of Data, and midnight ticks across partial days, DST and year boundaries.
Weather-symbol tests check descriptions, day/night variants, available native
symbols and accessibility labels. The UI test taps every selectable column header,
including horizontally scrolled headers, checks selection and chart titles, and
returns to the default temperature plot; Time remains non-interactive.
Fallback tests cover denied/restricted location, timeouts, recovery, exact Halifax
region matching, missing coordinate-lookup endpoints, manual overrides and stale
fallback responses. Granted location permission is reused without requesting it
again. The UI test denies
the normal location prompt and verifies the default forecast and manual selection.
For current-location UI tests, set the simulator's location to Halifax (44.65, -63.57);
the UI test accepts the normal When In Use permission prompt. Hourly-plot validation
passed 43 unit tests and all 7 UI scenarios on an isolated iPhone 17 Pro simulator.
The daily/hourly toggle test failed on the new simulator's first launch and passed
on a focused rerun alongside the new column-header test.
UI-test screenshots are attached to the test result

## Release scope

This is a runnable first native release, not an App Store submission. App Store
signing, a distribution profile, store metadata and public-server configuration
are deployment tasks. Fire-event detail pages, smoke job submission,
per-layer scale/cutoff overrides, downloaded offline regions,
push alerts and widgets remain follow-up features. All catalogue-exposed scalar
weather and smoke fields can already be selected.
